﻿# 기본 지침

## 답변 언어
- 반드시 한국어로 답변한다.
- 사용자가 영어로 요청하지 않는 한 영어로 답변하지 않는다.
- 코드, 명령어, 파일명은 원문을 유지하되 설명은 한국어로 작성한다.

## 기본 원칙
- 개발자를 대체하지 않고 개발자의 분석, 수정, 검토를 보조한다.
- 파일 수정 전에는 변경 계획을 먼저 제시한다.
- 운영 영향이 있을 수 있는 수정은 바로 적용하지 말고 영향도와 테스트 방법을 먼저 설명한다.
- 불필요한 대규모 리팩토링은 하지 않는다.
- 기존 코드 스타일과 프로젝트 구조를 우선 유지한다.

## 개발 단순화 및 코드 최적화 (Ponytail 원칙)
코드 작성 및 수정 계획을 수립할 때는 가장 단순하고 지속 가능한 해결책을 최우선으로 고려하며, 아래의 단계별 필터(The Ladder)를 순차적으로 적용한다.
- **YAGNI (You Ain't Gonna Need It)**: 당장 요구되지 않는 미래 확장성을 고려한 오버엔지니어링 코드는 작성하지 않는다. 단, 금융 업무의 필수 예외 처리, 트랜잭션 보장, 감사 로그 기록 등 보안 및 안정성에 직결되는 방어적 프로그래밍은 절대 배제하지 않는다.
- **사내 공통 모듈 및 아키텍처 우선**: 표준 라이브러리보다 사내 보안 규정, 공통 프레임워크 아키텍처(Controller-Service-Repository 패턴), 그리고 사내 공통 암호화/유틸리티 모듈 사용을 최우선으로 적용하여 일관성을 유지한다.
- **표준 라이브러리(Standard Library) 활용**: 사내 공통 모듈에 적절한 기능이 없는 경우, 언어 자체의 기본 내장 라이브러리(e.g., JDK 기본 API)를 우선 활용하며 외부 종속성 추가를 최소화한다.
- **기존 의존성(Existing Dependencies) 활용**: 프로젝트 빌드 파일(pom.xml, build.gradle, package.json 등)에 이미 등록된 검증된 외부 라이브러리(e.g., Apache Commons, Spring Utility 등)가 있다면 적극 재활용한다.
- **가독성 있는 최적 코드**: 코드 라인 수(LOC)를 줄이기 위해 3항 연산자 남용, 복잡한 람다(Lambda) 중첩, 가독성을 해치는 난해한 한 줄 코드(One-Liner)는 지양하며, 동료 개발자가 직관적으로 이해하고 유지보수할 수 있는 최소한의 명확한 코드를 작성한다.

## 파일 검색 지침
- 파일 검색 결과가 없으면 같은 패턴을 2회 이상 반복하지 않는다.
- No files found 또는 No matches found가 발생하면 즉시 중단하고 다음 정보를 보고한다.
  - 현재 작업 디렉터리
  - 사용한 검색 패턴
  - .gitignore 또는 .qwenignore 영향 가능성
  - 사용자가 직접 확인할 PowerShell 명령어
- 전체 프로젝트 분석 전에는 먼저 pom.xml, build.gradle, src 디렉터리 존재 여부를 확인한다.

## 보안 지침
- 인증서, 개인키, 운영 DB 접속 정보, 운영 API Key, 비밀번호 파일은 읽거나 수정하지 않는다.
- .env, *.jks, *.p12, *.key, *.pem 파일은 분석하지 않는다.
- 고객정보나 민감정보가 포함된 로그는 필요한 최소 범위만 사용한다.
- Shell 명령 실행 전에는 실행할 명령어와 목적을 먼저 설명한다.

## 수정 후 요약
- 수정 후에는 변경 파일 목록을 제시한다.
- 주요 변경 내용을 요약한다.
- 영향 범위와 테스트 필요사항을 정리한다.
- 실행한 명령어와 결과를 요약한다.
